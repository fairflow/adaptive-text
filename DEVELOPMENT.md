## The two implementations, and which one to extend

If you're adding a feature, decide first which path you're extending:

- Quick experiment / UI change → edit `adaptive_text_demo.py` directly
  (mocked transform logic in `mock_llm_transform()`).
- Real LLM behaviour change → edit `adaptive_text_integration.py`'s
  `AdaptiveTextProcessor`, or `processors/text_transformer.py`'s
  `TextTransformer` if you want the version with Anthropic support and the
  separated `database/persistence.py` layer. Note the demo scripts and the
  modular package currently duplicate logic (prompt-building, cost
  calculation) rather than sharing it — there's no single source of truth
  for the prompt template, for instance. Consolidating that would be a
  reasonable first refactor if you're picking this up.

## Setup

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

`requirements.txt` is pinned to specific versions (generated via
`pip freeze`), not range-specified, so it should install reproducibly on a
matching Python version. No `.python-version` or `pyproject.toml` is
present to pin the interpreter version itself.

## Running

```bash
streamlit run adaptive_text_demo.py          # mocked, no API key
OPENAI_API_KEY=sk-... python3 adaptive_text_integration.py   # real API calls
```

See `GUIDE.md` for details and `open adaptive-text-demo/index.html` for the
static mockup.

## Tests

```bash
pip install pytest   # not currently in requirements.txt
pytest tests/test_transform.py
```

As written, `test_transform.py` instantiates `TextTransformer()` with no
API key argument, so it falls back to `OPENAI_API_KEY` (or
`ANTHROPIC_API_KEY` if you pass `provider="anthropic"`) from the
environment and makes real, uncached-on-first-call API requests. There are
no mocks. Budget for that before running the suite, and don't wire this
into CI as-is without adding mocking or a recorded-fixture approach.
`tests/cache.py` is not part of the test suite despite its location — see
`MANUAL.md`.

## The espeak-ng submodule question

There is no espeak-ng submodule in this repo — no `.gitmodules`, no
submodule entry, no tracked reference to speech synthesis anywhere in the
codebase. The `espeak-ng/` directory visible in the working copy is a
separate, unrelated git checkout that happens to sit on disk in the same
parent folder. If a TTS/speech integration is planned for this project, it
does not exist yet in any form — it would be new work, not something to
"init" or "build" from an existing submodule.

## Build / deploy notes

- `adaptive-text-demo/index.html` has no build step and no dependencies —
  it's plain HTML/CSS/JS and can be served as a static file as-is.
- The Streamlit app (`adaptive_text_demo.py`) needs a Python runtime and
  the packages in `requirements.txt`; it is not a static build and cannot
  be exported to one, since the resolution/formality/reading-age
  transforms and the SQLite-backed wallet run server-side. `README.md`
  sketches Streamlit Cloud and Docker deployment options; neither a
  `Dockerfile` nor `docker-compose.yml` actually exists in the repo despite
  being shown as example snippets in `README.md` and
  `development-guide.md` — you'd need to add them.

## Contributing

This is a personal prototype repo, not one with a formal contribution
process — there's no `CONTRIBUTING.md`, issue template, or CI config
(no `.github/workflows` in this repo; don't confuse it with the workflows
inside the unrelated `espeak-ng/` checkout). If you're changing behaviour
shared between the two implementations (prompt wording, cost formula,
resolution/formality/reading-age definitions), update both
`adaptive_text_demo.py`/`adaptive_text_integration.py` and
`processors/text_transformer.py` — they are not currently kept in sync
automatically.
